# Checkpoint Protocol

## Storage and Identity

`scripts/checkpoint.py` uses Python 3's standard library on macOS/Linux. Default state directory: `${XDG_STATE_HOME:-~/.local/state}/email-triage`; use `--state-dir` for a user-selected private alternative or isolated tests. Runtime state never goes in the distributed skill or a project repository.

The helper uses POSIX `fcntl` locking and is not a native Windows implementation. Verify runtime support before relying on persistence; do not claim a durable checkpoint if the helper cannot run. Keep state private to the current user: sharing/installing the skill must not copy another user's checkpoint directory or seed their coverage. Users on a shared machine must use separate OS-user storage or separate private `--state-dir` locations.

One JSON file per SHA-256 of provider, normalized account identity, and scope. The provider and scope are saved; the raw account is not. Choose a stable verified account identifier, preferably the canonical mailbox address, and use it consistently across adapters. A scope describes actual coverage, for example `received-mail;all-folders;include-junk;exclude-deleted-drafts-sent-only;topics=all`. Discover folders each run. For a selected subset, include its stable folder IDs/names in the scope. Never include secrets or personal message contents in these arguments.

An older scope excluding Spam/Junk does not certify the newly included mail. Use the expanded scope with a stated baseline/backfill; do not copy its old checkpoint and claim historical Spam coverage. Account checkpoints remain independent: a successful account never advances a blocked or unreviewed account.

`covered_through` is the exclusive end of the fully checked interval beginning at `initial_since`. `last_attempt.window_end` freezes the upper bound when the run starts. There is deliberately **no task-completed timestamp used for continuation**. Before any success, `covered_through` is null.

## Commands

Substitute the skill's real path and the verified account/scope. Dates must be timezone-aware RFC3339. The helper stores UTC; present boundaries in the user's timezone. For an initial default lookback, compute seven days before the current instant; do not hard-code an example date as a live baseline.

```sh
python3 <skill-dir>/scripts/checkpoint.py show --provider outlook --account <account> --scope <scope>
python3 <skill-dir>/scripts/checkpoint.py begin --provider outlook --account <account> --scope <scope> --since <initial-start>
```

Use `--provider gmail` for Gmail and `--provider feishu` for Feishu Mail. Keep the provider and verified mailbox identity unchanged when switching supported access methods (Outlook/Gmail plugin/MCP to UI, or Feishu CLI to UI); the access method is not a new account. On subsequent runs omit `--since`:

```sh
python3 <skill-dir>/scripts/checkpoint.py begin --provider gmail --account <account> --scope <scope>
```

`begin` returns `run_id`, `new_since`, `window_start`, `window_end`, prior `covered_through`, and hashed `reported_keys`. The new review interval is `[new_since, window_end)`: the last successful boundary through the current run's start. Returning two days later therefore covers those entire two days. The wider retrieval interval starts at `window_start`, by default 24 hours before the checkpoint, never before `initial_since`. `--overlap-hours` may change the overlap for a documented sync issue. Review the whole retrieval interval but do not repeat unchanged findings already reported.

After enumerating and screening all messages, reading all relevant content, resolving thread status, and preparing the final report:

```sh
python3 <skill-dir>/scripts/checkpoint.py finish --provider gmail --account <account> --scope <scope> --run-id <run_id> --status complete --coverage-complete --report-ready
```

The flags are the agent's explicit assertions, not evidence generated by the script. The helper cannot inspect a mailbox or certify the quality of the review. Keep page/folder counts and unresolved gaps in the working context before asserting success. A completely reviewed empty interval is valid. Do not assert success merely because no relevant messages were found by a keyword query.

For a blocked or interrupted run:

```sh
python3 <skill-dir>/scripts/checkpoint.py finish --provider outlook --account <account> --scope <scope> --run-id <run_id> --status partial --reason "Result pagination incomplete"
```

This preserves `covered_through`. A new run restarts from the last successful boundary (or original baseline), not from the interrupted run's last visible message. A second `begin` on an in-progress stream is rejected. Inspect `show`; only mark an abandoned attempt partial after confirming no other agent is still using it. Do not silently steal or reset active runs.

Writes are file-locked and atomically replaced; mismatched or stale run IDs are rejected. Do not manually edit/reset state to overcome an error. Report the blocker and leave the checkpoint unchanged. A changed scope, account, or provider gets independent state; missing state requires a new explicit baseline, not an invented old checkpoint.

## Deduplication

Deduplicate fetched messages by the provider's stable ID, with thread context for status changes. To avoid repeating already prepared reports across the overlap, `finish --reported-id <opaque-id>` can be repeated for actionable source messages included in the report. Use the specific latest message ID, not just a thread ID. IDs are SHA-256 hashed on disk; retain at most the most recent 2,000 keys. Compare a candidate with `hashlib.sha256(id.encode()).hexdigest()` against `reported_keys`.

Only add keys when `--report-ready` is true (also allowed for a partial report). Never suppress a new reply, changed deadline, newly verified eligibility, or materially changed urgency solely because an older source was reported. If the adapter has no trustworthy stable ID, report deduplication uncertainty rather than using subject alone as identity. The ledger is a convenience, not a replacement for reading the latest thread.

## Account Inventory

`scripts/accounts.py` maintains `accounts.json` in the same private state directory. It requires Python 3.9+ and uses standard-library `zoneinfo` for Markdown display. The index contains provider, canonical account identity, optional human-readable label, and registered scope strings. It never stores coverage dates or copies checkpoint status. Unlike the hashed checkpoint filenames, this file contains readable mailbox identities: keep it private, outside repositories, and do not share its output publicly.

Register identities explicitly supplied by the user or discovered through authorized tools. This records a known account, not verified current access or permission to review it. Preserve the identity already used by a checkpoint; do not register a known alias as a separate mailbox. Existing hashed filenames cannot be reversed to discover unknown accounts. Do not infer an exhaustive inventory from them or automatically fill addresses from unrelated personal history.

```sh
python3 <skill-dir>/scripts/accounts.py register --provider outlook --account <account> --label "Work" --scope '<actual-scope>'
python3 <skill-dir>/scripts/accounts.py list --format json
python3 <skill-dir>/scripts/accounts.py list --format markdown --timezone Europe/London
```

Use the user's actual timezone. Both commands accept `--state-dir`; use the same directory as `checkpoint.py`. Repeated registration merges scopes and updates the label only when supplied. Omit `--scope` for a known account with no review scope yet; register each actual scope before its review, repeating `--scope` when needed. Registration does not begin, complete, or modify any checkpoint. It can associate an existing checkpoint with a known identity without migrating its file.

The JSON listing joins the index to live checkpoints and returns a separate row per account/scope, with `initial_since`, `covered_through`, and the last attempt. An account without scopes also appears. Missing checkpoints appear as `not_checked` with no completed date; partial attempts retain any previous successful coverage boundary. A malformed or unreadable checkpoint produces an `error` row and a nonzero CLI exit rather than an invented date. A corrupt index is not overwritten. The list is a per-file snapshot, not an atomic snapshot of all concurrently running reviews.

Markdown is rendered to standard output only; no `.md` or CSV mirror is maintained. Show both the scope and latest attempt status, rather than merging unrelated review streams into a single latest date. `list` neither checks live access nor modifies state. Run access preflight afresh before reviewing any requested account. Inventory membership does not expand the user's requested account set, and unknown or unavailable accounts must not be described as checked.

## Offline Acceptance Cases

Run `python3 -B -m unittest discover -s <skill-dir>/scripts -p 'test_*.py'`; tests use temporary directories and synthetic accounts, never a real mailbox. Also review these behavioral cases:

- Important received mail routed to a custom folder is included; Inbox-only success is invalid for whole-mailbox scope.
- A legitimate notice misclassified as Spam/Junk is screened; default search excluding Spam cannot establish complete coverage.
- An all-account request finds two Gmail accounts and one Outlook account, but one is inaccessible: report per-account coverage and the gap, never claim all accounts complete.
- Outlook is unconfigured while Gmail is connected: Outlook goes to its authorized UI, not the Gmail account.
- Feishu CLI is usable: read `lark-shared` and `lark-mail`, verify the target mailbox, and use CLI without searching for a Feishu plugin/MCP; a default inbox-only `+triage` result does not certify full coverage.
- Feishu CLI authenticates as one user but the requested shared mailbox is inaccessible: report the target-specific gap; do not substitute `me` or silently elevate to bot identity.
- Feishu discovery returns a personal mailbox and two public mailboxes: review all three for a general Feishu request, keep explicit targets and independent checkpoints, and do not count sender aliases as extra accounts.
- A configured connector is permission-denied: explain the access boundary; do not silently bypass it.
- A newsletter mentions a paid internship but the official page requires a final-year student: eligibility stays explicit, not assumed from the subject.
- A newer reply says the problem is resolved: do not surface the older alert as still requiring action.
- One folder/page/body is inaccessible: report known findings with a partial result and preserve the prior boundary.
- A topic-only review or backfill does not advance the general mailbox stream.
